Initializers and integrated toolchains

bun init -y projects/game-backend generates a Bun package, TypeScript configuration, and starter files and installs dependencies. Start there and inspect the result before adapting scripts. Generated defaults are version-specific and runtime-specific. Bun init.

Vite+ scaffolds applications, libraries, and monorepos with vp create or bun create vite-plus. Its check command combines formatting and linting with type checking when configured; scaffolding enables the relevant type-aware settings by default. Tests are a separate vp test command. Create · Check.

Distinguish built-ins from tasks: vp dev runs Vite's dev server; vp run dev invokes a custom dev task. vp build builds web apps; vp pack handles library/executable packaging. Select a backend build/start workflow intentionally instead of assuming a frontend template supplies one. Dev · Run · Pack.

Where Node.js differs

For a conventional emitted-JavaScript Node backend: install a supported Node version, use an ESM package, configure TypeScript module and moduleResolution to NodeNext, and emit into dist. Relative imports must match Node's runtime resolution, commonly using .js specifiers in TypeScript source. Use tsc -p tsconfig.json for build and node dist/index.js to start. A development runner or separate compile-and-restart watchers complete that workflow. Recent Node releases also support running a subset of TypeScript directly, with constraints and no type checking. Node: native TypeScript · TypeScript: Node module modes.

Production learning sequence

This is the planned progression, not a claim that the small package implements these capabilities.

  1. Modules and tests: keep deterministic game rules separate from HTTP, storage, and configuration; test outcomes and boundaries.
  2. Input and errors: validate untrusted data at runtime, distinguish expected failures from defects, and map errors to deliberate HTTP responses.
  3. Async and HTTP: await I/O, handle rejected promises, add timeouts, limit request sizes, and avoid blocking the event loop.
  4. Operations: validate configuration at startup; write structured logs with request IDs and secret redaction; expose appropriate health/readiness signals; drain work on shutdown.
  5. Reproducible delivery: pin runtime/tool versions, install from a frozen lockfile, check types and formatting/lint, run unit and HTTP tests, build once, smoke-test the artifact, and deploy the same artifact with rollback support.
  6. Persistence and access: migrations, transactions, authentication/authorization where needed, rate limits, monitoring, backups, and tested recovery.

Primary operational starting point: Bun server lifecycle. We will select deployment/database documentation when those choices become concrete.
