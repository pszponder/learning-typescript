Readonly and runtime freezing

Your win: Protect a game-state API from accidental mutation.

Readonly types restrict writes through a reference during checking. ReadonlyArray<T>, ReadonlyMap<K, V>, and ReadonlySet<T> expose reading operations; they do not freeze the underlying values. Another mutable alias can still change the collection. JavaScript has no built-in frozen Map or Set equivalent to Python’s frozenset. Object.freeze is shallow and freezes ordinary properties; it does not disable Map.set or Set.add.

// Track which object each reference reaches; a shallow copy can share nested data.
const mutable = new Set<string>(["ada"]);
const view: ReadonlySet<string> = mutable;
// view.add("lin"); // checker rejects this
mutable.add("lin");
console.log(view.has("lin")); // true

const frozen = Object.freeze(new Map<string, number>());
frozen.set("ada", 2); // entries can still change
console.log(frozen.get("ada")); // 2
const modes = ["waiting", "playing"] as const;
console.log(modes[0]);

as const keeps literal types and readonly literal structure at checking time; it does not freeze runtime objects. For an independent snapshot, copy the collection, then expose a readonly view. That copy is shallow: object elements can remain shared. For runtime entry immutability, use an API that hides mutation or a suitable immutable collection implementation.

const source = new Map<string, number>([["ada", 2]]);
const view: ReadonlyMap<string, number> = source;
const snapshot: ReadonlyMap<string, number> = new Map(source);

console.log(view.get("ada"), snapshot.get("ada"));

5 2

  2. new Map(source) copies the entries into a separate map. Numeric values need no nested copying.
  3. Updating source is visible through view but not through snapshot.
