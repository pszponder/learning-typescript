Work across files

Your win: separate reusable game rules from the file that runs them.

Files with import or export are modules with their own scope. Export exposes selected declarations; import names what another module uses. Keep game rules separate from startup code so a future HTTP handler can reuse them. TypeScript modules.

// messages.ts
export type Turn = "again" | "finished";

export function nextTurn(lives: number): Turn {
  return lives > 0 ? "again" : "finished";
}

// main.ts (a separate file beside messages.ts)
import { nextTurn } from "./messages";
import type { Turn } from "./messages";

const turn: Turn = nextTurn(2);
console.log(turn);

These are two files, not one pasted block. Named exports use braces in the import. A default export, such as export default nextTurn, is imported without braces and may be given a local name. Use named exports here. import type imports a type for checking and disappears at runtime. ./ refers to the importing file's directory. Nub supports extensionless relative imports; Node emitted-JavaScript setups need their own resolution rules. MDN modules.

Worked example: follow the values

Read this as a separate small program. Predict its output before opening the explanation.

// In this example, type and value exports share one module.
export type Badge = "bronze" | "gold";
export function badgeFor(points: number): Badge {
  return points >= 10 ? "gold" : "bronze";
}
console.log(badgeFor(9), badgeFor(10));
Reveal the output and walkthrough
bronze gold
  1. The type export describes allowed strings to the checker; the function export is a runtime value.
  2. An export does not call the function. The demonstration logs are what execute it here.
  3. For the two-file practice, move those logs to the entry point so importing rules does not also run a demonstration.
