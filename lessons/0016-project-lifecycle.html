Check, build, watch, run

Your win: create a small project and distinguish source execution from a built artifact.

Our environment supplies Nub, Node.js, and TypeScript. Nub runs TypeScript on Node with transpilation and resolution helpers; keep type checking as a separate step. NODE_EXECUTABLE selects the Nix-provided Node. Nub runtime.

Four separate jobs

  • Typecheck: check types without emitting files.
  • Build: emit JavaScript into dist.
  • Run: execute source or an existing artifact.
  • Watch: repeat an operation after changes.

1. Initialize, then inspect

From the repository root, use Nub's initializer to generate package.json, tsconfig.json, an entry point, and development dependencies. Skip nested git initialization inside this teaching repository. Nub init.

mkdir -p projects/game-backend
cd projects/game-backend
nub init -y --no-git
mkdir -p src tests

Inspect the generated files and preserve their dependencies and package-manager pin. Move index.ts into src/index.ts and adapt the metadata and scripts:

{
  "name": "game-backend",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "nub watch src/index.ts",
    "typecheck": "tsc --noEmit",
    "typecheck:watch": "tsc --noEmit --watch",
    "build": "tsc -p tsconfig.json",
    "start": "node dist/src/index.js",
    "test": "nub run build && node --test dist/tests/rules.test.js",
    "check": "nub run typecheck && nub run test"
  }
}

Commit package.json and the generated nub.lock. Use nub ci for a frozen installation in CI. Commit devenv.lock to record environment inputs; record nub --version and node --version when matching deployment tools. Nub dependencies.

2. Configure an emitted-JavaScript project

Replace the generated tsconfig.json with this configuration: it enables emission for our build instead of the scaffold’s noEmit setup. This build emits files separately; it does not bundle them.

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "rootDir": ".",
    "outDir": "dist",
    "strict": true,
    "noEmitOnError": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noFallthroughCasesInSwitch": true,
    "verbatimModuleSyntax": true,
    "sourceMap": true,
    "types": ["node"],
    "skipLibCheck": true
  },
  "include": ["src/**/*.ts", "tests/**/*.ts"]
}

NodeNext follows Node's module rules. With type: module, use "./rules.js" in TypeScript imports: the checker finds rules.ts while the emitted import points to rules.js. Nub supports TypeScript-friendly resolution for source execution. rootDir preserves src and tests beneath dist. noEmitOnError prevents emission on compiler errors. 3. Write your entry point and tests

Copy your judgeGuess implementation into src/rules.ts and export it. Remove demonstration logs. In src/index.ts import it from "./rules.js", call it, and log the result.

Create tests/rules.test.ts. Import your rule from "../src/rules.js" and write one assertion for each outcome. Use this small test pattern, replacing the arithmetic assertion with your own:

// Keep rule behavior separate from the commands that check and execute it.
import { test } from "node:test";
import { strict as assert } from "node:assert";

test("example assertion", () => {
  assert.equal(2 + 2, 4);
});

Tests run against the emitted JavaScript using Node's test runner. Keep game-rule code learner-owned; ask the agent to review your attempt.

4. Observe the feedback loop

  1. Run nub run check. Checking, compilation, and tests should pass.
  2. Run nub run start. The built entry point prints your result, then exits.
  3. Run nub run dev and, in a second terminal in the same package, nub run typecheck:watch. Change a log message. Execution restarts while checking runs independently. Stop both with Ctrl+C.
  4. Run start without rebuilding: it prints the old artifact's message. Run build, then start: the message changes.
  5. Pass a string to a numeric parameter temporarily. Observe the checker error, then restore the valid call.

nub watch restarts source execution; it does not update dist or replace tsc. Runtime and watch documentation.

More practice: diagnose the workflow

Use your own package after completing the main exercise. This is an optional second session.

1. Predict

After changing source, run typecheck without build. Which message should start print?

Check

The old built message. Typecheck emits nothing.

2. Introduce and repair one type error

After a successful build, pass a string to a numeric rule parameter. Run typecheck, then build. Record both diagnostics. Do not start the invalid source. Restore the valid call and rebuild.

Expected observation

Both checking and building fail; noEmitOnError prevents new output on the failed build. Previous artifacts may still exist, so their presence is not evidence of a successful current build.

3. Add a meaningful test

Add a test for a boundary that your current game rule has not covered, explain the expected result, and run nub run check. Temporarily change only the assertion’s expected value so the test fails; restore it afterward.

Hint

Use equality with the secret or a negative input if that is within your rule’s contract. Inspect the test failure rather than treating any output as success.

Success criteria: you can distinguish a compiler error from an assertion failure, identify which command refreshes dist, and explain which file start executes. Ask the agent to review your package scripts and observations.
