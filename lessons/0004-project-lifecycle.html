04 / Backend foundations / About 15 minutes

Check, build, watch, run

Your win: create a small project and observe the difference between source execution and a built artifact.

We use Bun because this workspace provides it. This is one coherent backend workflow; see the reference for the Node.js alternative. We start with a game-rule entry point before adding HTTP.

Four separate jobs

  • Typecheck: ask TypeScript to reject invalid code without emitting files.
  • Build: transform and bundle source into a JavaScript artifact.
  • Run: execute source or an artifact in a runtime.
  • Watch: repeat an operation when files change.

Plain Bun execution transpiles TypeScript without type checking. We explicitly run tsc before building. Newer Bun versions also offer opt-in checking; keeping a named typecheck command makes this contract clear. Bun and TypeScript · Opt-in checking.

1. Scaffold, then inspect

Use Bun's initializer rather than authoring the starter configuration by hand. From the repository root, run:

bun init -y projects/game-backend
cd projects/game-backend

It generates package.json, a Bun-oriented tsconfig.json, an entry point, and supporting files, then installs development dependencies. Interactive bun init lets you choose a template; use Blank for this exercise. Exact defaults vary by Bun version. Bun initializer.

Create src and tests directories. Move the generated entry point to src/index.ts and update any generated package entry-point field that still refers to the old path. Inspect the generated scripts and configuration first; then adapt them to this lesson. Preserve the generated dependencies. The following shows our desired package metadata and scripts, not a replacement for the whole generated manifest:

{
  "name": "game-backend",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "bun --watch src/index.ts",
    "typecheck": "tsc --noEmit",
    "typecheck:watch": "tsc --noEmit --watch",
    "build": "bun run typecheck && bun build src/index.ts --target=bun --outdir=dist --sourcemap=linked",
    "start": "bun dist/index.js",
    "test": "bun test",
    "check": "bun run typecheck && bun run test && bun run build"
  }
}

The initializer installs TypeScript and Bun definitions. You do not need a second installation just to begin. If you want exact manifest versions instead of ranges, run bun add --dev --exact typescript @types/bun; bun.lock already records the resolved dependency graph.

Commit package.json and bun.lock. The local TypeScript version is what package scripts use. Record the exact output of bun --version as package.json's packageManager, for example "bun@1.4.4" for this session, and use that same version in CI and deployment. That field documents the version; your environment must actually install it. Install and lockfile documentation.

2. Understand the generated tsconfig.json

Bun supplies recommended defaults for its runtime, not a universal TypeScript configuration. Compare the generated file with this lesson's configuration. Adapt it deliberately for our source/test directories and strictness; you do not need to memorize or type every option.

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "Preserve",
    "moduleResolution": "bundler",
    "strict": true,
    "noEmit": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "noFallthroughCasesInSwitch": true,
    "verbatimModuleSyntax": true,
    "types": [
      "bun"
    ],
    "skipLibCheck": true
  },
  "include": [
    "src/**/*.ts",
    "tests/**/*.ts"
  ]
}

Strict checking is the baseline. Unchecked indexed access adds undefined to possibly absent array/object lookups. Exact optional properties distinguishes omission from an explicitly assigned undefined. Preserve/bundler matches this Bun workflow; do not copy it unchanged to a Node project emitting code with tsc. skipLibCheck skips declaration-file checking, not your application code. TSConfig reference.

3. Supply your own entry point and test

Copy your judgeGuess implementation into src/rules.ts and export the function. Remove its demonstration logs from that module. In src/index.ts, import it from "./rules", call it, and log the result. Bun resolves this extensionless import. Module resolution.

Create tests/rules.test.ts. Import test and expect from "bun:test", and your rule from "../src/rules". Write one test for each outcome; start with this pattern:

import { expect, test } from "bun:test";

test("example assertion", () => {
  expect(2 + 2).toBe(4);
});

Replace the example with your own game-rule assertions. Bun test runner.

4. Observe the feedback loop

  1. Run bun run check. Type checking, tests, and build should all pass.
  2. Run bun run start. It should print your game result, then exit. This entry point is not yet a long-running HTTP server.
  3. Run bun run dev and, in another terminal in the same package directory, bun run typecheck:watch. Edit a log message and save. Watch restarts execution; the checker watches independently. Stop each with Ctrl+C.
  4. Run start again without rebuilding. It still prints the old artifact's message. Build, then start: now the message changes.
  5. Temporarily pass a string to a numeric parameter. Observe the checker error; plain source execution may still run. Restore the valid call.

--watch restarts the process; --hot has different state-preserving behavior. Restarting is a useful baseline for backend development. Watch modes.

What about Vite+?

Vite+ is a broader integrated toolchain: project scaffolding, formatting, linting, type checking, tests, builds, and task execution. Its documented Bun entry point is bun create vite-plus; with the global CLI, use vp create. Creating a Vite+ project.

It is useful when you want a coordinated toolchain for a larger app, library, or monorepo. It can also coordinate custom backend scripts, but its built-in vp dev starts Vite; vp run dev runs your project's dev task. Those are different operations. A backend still needs an explicit server runtime, build target, and start command. Dev · Run.

For this first Bun game backend, start with bun init so the runtime and command lifecycle stay easy to inspect. Vite+ is a reasonable next comparison when adding formatting/linting or a web client. This is a teaching choice, not a requirement that production backends use Bun-only tooling.

Keep generated files separate

Add these patterns to the package's .gitignore. Commit an .env.example with placeholders when configuration arrives; inject real secrets at runtime.

node_modules/
dist/
.env
.env.*
!.env.example

A Bun backend can also run TypeScript source in production; bundling is a deployment choice. Here the artifact makes the lifecycle visible. A successful build alone does not make the service production-ready.
