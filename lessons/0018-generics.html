Generics: preserve the element type

Your win: Reuse a collection helper without losing type information.

Optional later topic. Study this when a project needs it; it is not required before the main-path modules, async, or workflow lessons.

A type parameter connects the types used by a function. T stands for an element type selected or inferred for a call; it does not create a runtime type value. ReadonlyArray<T> already uses this idea. Generics preserve relationships that any would discard.

// The type parameter preserves relationships between input and output types.
function first<T>(items: readonly T[]): T | undefined {
  return items[0];
}
const score = first([3, 7]);
const player = first(["Ada", "Lin"]);
console.log(score, player, first<number>([])); // 3, Ada, undefined

function named<T extends { name: string }>(value: T): string {
  return value.name;
}
console.log(named({ name: "Ada", score: 3 }));

An unconstrained T gives no promise about name or other fields. extends supplies the capability a helper requires. A return type of T | undefined honestly represents an empty collection. Generics do not validate JSON and usually do not require explicit type arguments when inference has enough information.

What preserves the link between input and output types?

Worked example: follow the values

Read this as a separate small program. Predict its output before opening the explanation.

// The type parameter preserves relationships between input and output types.
function pairWith<T>(item: T, label: string): { item: T; label: string } {
  return { item, label };
}
const numeric = pairWith(7, "score");
const named = pairWith("Ada", "player");
console.log(numeric.item + 1, named.item.toUpperCase());
Reveal the output and walkthrough
8 ADA
  1. The first call infers T as number; its returned item remains numeric.
  2. The second infers T as string; the returned item supports string methods.
  3. The generic connects input and output types without inspecting types at runtime.
